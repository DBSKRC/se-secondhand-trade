# 校内二手交易系统面向对象设计实验报告

## 一 实验目的与项目说明

本实验承接实验一《二手交易系统需求说明书》v1.0，将需求转化为模块、对象、数据结构和界面。实验目标是掌握面向对象设计方法，使用 PlantUML 表达静态结构、行为与交互，并通过可编辑界面原型检查功能是否可用、业务流程是否完整。

项目面向校园闲置物品交易，界面暂用名“校园拾光”。普通账号同时承担买家和卖家角色，管理员采用独立权限。系统负责商品发布与审核、条件查询、预约、线下交付状态记录、举报和审计。支付、退款、物流、站内聊天和收藏未纳入本次范围；双方在系统外联系和交付。商品价格是预约依据，不是系统收款金额。

本报告依据实验一仓库中的 requirements.md 和 chat.txt。需求已确认部分作为设计基线；未确认部分采用显式标注的暂定方案。实验二交付设计原型及图文材料，不将原型截图解释为已经运行并通过验收的业务系统。封面学号与姓名由最终提交者核对填写。

## 二 主要功能与模块划分

### 2.1 账号与权限

游客可查询和查看公开商品，发布、预约、举报及查看个人记录必须登录。普通用户在同一账号内切换“买入”和“卖出”视角，不切换数据库权限。管理员不能通过管理页面修改卖家的商品正文。每次操作都由服务端检查登录态、角色、资源归属和当前状态，页面隐藏按钮仅用于引导。

### 2.2 商品管理与查询

卖家填写标题、描述、分类、价格、成色和图片，保存草稿后提交审核；通过后进入公开列表，驳回则展示原因并允许修改重提。已发布且无有效预约时可修改或下架。已预约或交易中不得改价、删除或主动下架。标题、分类、价格、主要描述变化暂按重新审核处理，其余字段变化是否重审继续待确认。

查询支持关键词、分类、最低价、最高价与状态组合，条件取交集。普通买家列表固定限制为已发布且可预约；个人记录与管理端在授权范围内展示其他状态。价格区间非法时定位到输入字段。排序、每页条数以及默认顺序尚未确认，原型不把推荐算法、销量排序或分页规则当作既定业务。

### 2.3 预约与交易

买家预约时确认商品版本和显示价格。创建预约同时保存价格快照、买家、商品及时间，商品变为已预约。卖家接受后双方进入交易中；卖家标记交付后等待买家确认，只有买家确认才完成交易。卖家接受之前允许买家取消、卖家拒绝；记录保留，商品恢复发布。交易中普通取消不可用，需要管理员介入。买家在待确认交付阶段提出争议后转入待管理员处理。

### 2.4 审核与治理

管理员审核商品、填写驳回原因，按权限下架或冻结违规商品，处理举报及记录争议处理结果。举报原因、处理结果和冻结原因分别校验，不能用一个含糊的“已处理”替代实际意见。争议处理目前只记录结果，不提供未经确认的强制结案、强制完成或解冻入口。

### 2.5 统计与日志

卖家查看自己商品总数、各状态数及完成交易数。管理员按时间、分类、状态查询商品、预约、完成与举报处理汇总。关键业务和安全事件记录操作者、对象、动作、结果和时间；状态变化保存前后状态。日志只供授权管理员查询，不提供修改删除入口。

## 三 总体架构与模块交互

采用分层的模块化单体。表示层包含手机尺寸用户原型和桌面管理后台；应用服务层包含账号、商品、查询、预约交易、审核治理、统计与日志服务；领域层封装状态规则；数据访问层通过仓储读写关系数据库，图片文件独立存储，库内保存路径与元数据。

这种设计适合课程项目规模：业务边界可辨认，部署不需要拆成多个网络服务，商品与预约可以共享本地事务。微服务会增加分布式一致性和部署成本，当前规模没有对应收益。界面只发送业务命令，不直接决定状态；仓储只负责持久化，不决定某个买家能否确认交易。

主要交互包括：账号服务为业务请求提供可信身份；商品服务调用审核服务建立审核任务，审核通过由受控命令推进商品状态；预约交易服务协调商品、预约、有效占用记录和操作日志；治理服务通过同一业务入口冻结商品，避免直接更新数据库导致交易失配；统计服务读取授权数据视图，不反向改变业务状态。定时任务通过预约服务关闭过期预约，而不绕过领域校验。

类图描述对象属性、行为及基数；组件图解释上述依赖；用例图说明参与者边界；活动图展示发布至完成的跨角色流程；商品和预约状态图区分两套状态；时序图展开预约请求中的鉴权、去重、版本核对、锁与事务。所有图均保留同名 .puml 与渲染 PNG。状态图两张仍属于同一种 UML 类型，时序图与序列图不重复计数。

## 四 面向对象职责与状态规则

User 保存账号标识和角色，普通账号的买家、卖家身份由参与的关联决定，不建两个互不关联的账号实体。Product 保存卖家、分类、描述、价格、状态及版本，封装提交审核、下架等状态约束。Reservation 关联一个商品和一个买家，保存价格快照和生命周期时间，封装确认、取消、交付、完成等转换。商品与历史预约是一对多，不可为实现唯一性而删除旧记录。

ReviewRecord 表达某次审核结论和原因，Report 表达举报及处理，Dispute 表达交易争议及处理意见，OperationLog 表达可追溯事件。服务类协调多个实体，仓储接口隔离存储实现；状态枚举限制合法值，实体方法限制合法路径。这样既避免所有规则堆在控制器中，也避免一个庞大的“系统管理类”拥有全部职责。

| 业务动作 | 预约结果 | 商品结果 |
|---|---|---|
| 创建预约 | 待卖家确认 | 已预约 |
| 买家取消或卖家拒绝 | 已取消或已拒绝 | 已发布 |
| 卖家接受 | 交易中 | 交易中 |
| 卖家标记交付 | 待买家确认 | 交易中 |
| 买家确认完成 | 已完成 | 已完成 |
| 买家提出争议 | 待管理员处理 | 交易中 |
| 超时关闭，暂定规则 | 已取消，原因超时 | 已发布 |
| 冻结尚未确认的预约，暂定规则 | 已取消，原因冻结 | 违规冻结 |
| 冻结交易中商品，暂定规则 | 待管理员处理 | 违规冻结 |

商品“已完成”和预约“已完成、已取消、已拒绝”是终态。待管理员处理不能自行回到可预约。有效预约定义为待卖家确认、交易中、待买家确认、待管理员处理；争议中的商品仍占用，防止二次售卖。冻结的具体入口和恢复规则存在基线冲突，表中对应路径是待确认设计，不能称为甲方最终确认。

## 五 数据存储与一致性设计

暂选 PostgreSQL 关系数据库作为可实施方案，框架及语言留待实验三选择。金额使用 NUMERIC(12,2)，不使用二进制浮点；时间统一以带时区时间戳保存，界面按北京时间显示。账号密码仅存加盐哈希，不写入日志。以下字段是设计，不代表已建立数据库。

| 表 | 主要字段与约束 |
|---|---|
| users | id主键，account唯一非空，password_hash，role，created_at；注册字段暂定 |
| categories | id主键，name；分类集合以最终业务确认为准 |
| products | id主键，seller_id外键，category_id外键，title，description，price，condition，status，version，created_at，updated_at |
| product_images | id主键，product_id外键，storage_path，position；图片与商品一对多 |
| reservations | id主键，product_id外键，buyer_id外键，price_snapshot，product_version，status，created_at，updated_at，expires_at，completed_at，close_reason |
| active_reservations | product_id主键，reservation_id唯一外键；仅保留有效占用，历史仍在reservations |
| review_records | id主键，product_id，reviewer_id，action，reason，created_at |
| reports | id主键，reporter_id，product_id，reason，status，handler_id，result，created_at，handled_at |
| disputes | id主键，reservation_id外键，initiator_id，reason，handler_id，handling_result，created_at，handled_at；不预设强制结案状态 |
| operation_logs | id主键，actor_id可空，actor_type，object_type，object_id，action，result，before_state，after_state，created_at，request_id |
| idempotency_requests | actor_id、operation、request_key联合唯一，payload_hash，result_reference，response_summary，created_at |
| system_config | key主键，value，description；保存暂定预约时限等参数 |

外键禁止因删用户或商品而级联删除交易、举报或日志；业务页面不提供破坏历史的删除行为。active_reservations 的商品主键从数据库层保证每商品最多一个有效占用，因此也保证同买家对同商品无重复有效预约。占用表须关联与商品匹配的预约：reservations 增加(product_id,id)唯一键，以组合外键保证匹配。有效状态与占用记录的存在性由事务业务方法维护并通过一致性检查核对，不能声称单凭一条唯一索引已覆盖全部状态关系。

商品查询建立(status,category_id,price)组合索引，个人商品建立(seller_id,status)，预约建立(buyer_id,status)与(product_id,created_at)，举报建立(status,created_at)，日志建立(created_at)、(actor_id,created_at)和(object_type,object_id)。关键词可先采用受控查询；中文分词与全文索引方案在性能环境确认后选择，不预先宣称达到性能指标。

预约请求携带 request_key、product_version、confirmed_price。服务端先鉴权，再检查同用户同动作的幂等键；已成功且参数一致则返回原结果，键相同而参数不同则拒绝。事务按商品、预约的固定顺序加行锁，重新读取状态和价格版本。同买家已存在有效预约时返回原预约；否则核对当前可预约及确认价格，创建预约、插入有效占用、更新商品、写业务日志与幂等结果，一并提交。任一步失败整体回滚。不同买家竞争同一商品，只有持锁后仍满足条件的请求成功。

修改商品也先锁商品并增加版本。若改价先完成，预约遇到版本或价格不符应要求重新查看并确认，而不是悄悄采用新价；若预约先完成，修改因状态限制被拒绝。取消与接受、超时与接受使用相同锁顺序及当前状态守卫，只允许一个命令成功。取消、拒绝、超时关闭时释放占用；冻结取消时商品保持冻结，不能套用普通取消的恢复发布逻辑。

成功业务日志与业务更新同事务提交。鉴权失败或回滚事件另走受控审计通道，以免失败日志随事务回滚而丢失；不得记录密码或完整敏感请求。后台任务操作者标记为系统。关键请求失败返回可理解原因及请求编号，供查询日志。

## 六 UI设计与交互说明

用户端采用手机尺寸，管理员采用桌面布局。视觉保留暖白与酒红，页面借鉴二手平台的搜索、分类和商品卡片组织，不照搬支付、物流或聊天流程。首页压缩宣传面积，使真实商品图、标题、价格和成色先被看见。主色用于当前导航、主操作和价格重点，危险操作同时标文字，不只靠颜色区分。

六张商品实拍由用户提供，界面中的价格、账号、数量和状态是演示数据，不能据图推断真实售价或物品情况。拍到包装盒的图片保留其原貌，不将其处理成实际物品照片。头像可用昵称首字，不伪造学校认证或信用背书。

| 页面组 | 功能与关键状态 |
|---|---|
| 登录与注册 | 账号密码表单，重复账号及字段错误；注册字段注明暂定，不标“已完成校园认证” |
| 首页与查询筛选 | 搜索、分类、价格上下界；公开状态固定为可预约；无匹配结果有清空条件入口 |
| 商品详情 | 大图、价格、成色、描述、卖家昵称；预约确认显示当前价格；举报需登录 |
| 举报表单 | 必填原因，提交后显示已收到，不增加尚未确认的举报进度查询 |
| 发布与编辑 | 图片、标题、分类、成色、描述、价格；草稿与提交审核分开；非法金额定位字段 |
| 我的商品 | 按九种状态查看，驳回展示原因；已预约和交易中解释编辑限制 |
| 买入与卖出预约 | 分身份查看待处理及历史记录；取消、接受、拒绝依据当前状态显示 |
| 交易详情 | 预约编号、快照价格、进度和双方职责；卖家交付不直接显示交易完成 |
| 提出争议 | 说明争议原因，提交后进入待管理员处理，不显示未经确定的强制结案结果 |
| 个人中心与统计 | 我的商品、买入卖出、个人范围统计和退出登录；无数据展示零值 |
| 管理审核 | 列表与商品详情并列，通过或填写原因驳回，无法编辑卖家正文 |
| 管理商品 | 状态筛选、商品详情、下架与冻结原因；冻结路径标注暂定方案 |
| 举报处理 | 举报事实、商品、原因、处理结果；必要时调用商品治理命令 |
| 争议处理 | 查看原交易与争议说明，记录处理意见；不自动恢复商品可预约 |
| 管理统计 | 时间、分类、状态筛选；展示口径及示例数，不提供未确认的导出 |
| 日志查询 | 按时间、操作者、动作和对象筛选，只读展示变更前后状态 |

底部导航采用首页、发布、交易、我的；发布和交易需要登录。每屏只保留清晰的主操作，长表单允许滚动。原因输入、拒绝及冻结应有明确对象和二次核对。加载、空列表、成功、字段错误、权限失效与旧页面冲突均需要反馈，不以页面静止代替处理结果。

后续实现应以角色越权、并发预约、取消与接受竞争、价格变动旧页请求及事务故障注入作为重点验证。实验一提出的百轮并发预约及查询性能指标是后续验证计划，本报告没有运行系统，不能将设计检查写成这些测试已通过。

## 八 待确认事项与基线歧义

REQ-027前置条件只写已发布或已预约，正常结果和验收却覆盖交易中冻结；REQ-006与REQ-013的冻结入口也比该场景窄。本次暂拟支持交易中冻结并转人工处理，图中用注释区分，最终入口需确认。REQ-029称预约转交易中时商品可以已预约或交易中，与REQ-011同步进入交易中不够一致，本次采用REQ-011的严格对应关系。

普通取消恢复发布的表述不适用于冻结取消，因此必须区分关闭原因和事务入口。商品已下架后的重新上架路径、冻结恢复路径、争议处理后出口尚未定义，不在原型增加快捷恢复按钮。已发布商品仅补图片是否重审、零价是否允许、校园身份验证、举报重复合并、日志保留、统计时间口径、分页排序、性能环境均保持待确认。

预约24小时设为可配置示例，系统关闭原因与买家主动取消不同。统计暂按商品创建时间筛选商品集合、预约创建时间筛选预约集合、完成时间筛选完成数量、举报提交时间筛选举报集合；这是为消除歧义提出的设计口径，需业务确认。原型不把“交易金额”当作平台收入。

## 九 AI辅助过程与工作流反思

本实验使用主协作代理组织专项子代理完成初稿，再由代理审查、修订，最终交学生审阅。AI交互记录收录专项任务指令、子代理产出及审查反馈，不收录学生与主协作代理之间的聊天。以下分析是代理形成的设计分析，不预先声称学生已经独立验证、修改或完成最终人工检查。

需求设计子代理读取需求说明和原访谈，生成模块、数据表、覆盖矩阵及本报告主体；UML子代理依据相同基线生成PlantUML。结构化生成有利于快速列全对象和字段，但容易把常见电商功能带入项目，或把待确认内容写成定论。因此任务约束明确排除支付物流聊天，要求每条需求有落点，并保留冲突。每次真实交互另存协作记录，后续审查填写实际问题与对应修改，不编造未发生的工具调用。

AI的优势是快速形成多种视角、统一重复结构，并将需求追踪到图和页面。局限是语法正确不等于业务正确：它可能遗漏失败分支，误用继承与关联，把截图中的演示数据当作真实信息，或以一个“已处理”隐藏尚无规则的争议出口。界面生成也容易偏重宣传图而弱化搜索和状态，必须以可操作任务检查密度和按钮位置。

可采用“需求基线锁定—专项生成—跨产物核对—渲染检查—差异修订—学生审阅”的工作流。初稿和修订分别形成真实本地Git提交，提交说明区分生成与代理修订。技术检查可自动化：PlantUML渲染、文件完整性、需求编号覆盖、图文状态名称一致、图片清晰度和版面溢出。学生则集中确认业务取舍、未决规则、视觉偏好及报告是否准确表达自己的理解。

人只做检查校对可以大幅减少重复劳动，但不能把“批准”简化为不读内容的一次点击。需求有矛盾时需要有权作业务决定的人确认；美观度、易用性和范围是否合适也依赖目标用户判断。因此工作流适合让代理承担制作和初审，让人保留最终判断与责任，而非把代理审查伪记成人工修改。

## 十 结语与后续工作

本次设计以商品和预约状态的一致性为主线，使用分层模块、领域对象、事务约束和双端界面共同表达业务。后续实验可按账号、商品审核、预约交易、治理统计的顺序实现，优先解决待确认规则，并以同一套状态对照表维护设计与实现的一致性。
